# About The Benchmark

This document provides a detailed overview of the Multilingual Tokenizer Leaderboard, including its purpose, the metrics used for evaluation, and the composition of the benchmark dataset.

## What is this benchmark?

The Multilingual Tokenizer Leaderboard is a comprehensive platform for evaluating and comparing the performance of Hugging Face tokenizers across a wide range of languages and text domains. The primary goal is to understand how different tokenization strategies impact efficiency, which is crucial for training and deploying large language models.

Tokenizer efficiency directly affects:
*   **Computational Cost**: More tokens mean longer sequences, which increases the computational requirements for training and inference.
*   **Model Performance**: Suboptimal tokenization can lead to a model struggling with certain languages or concepts, effectively making it "see" more complex input than necessary.
*   **Memory Usage**: Longer token sequences require more memory.

This leaderboard was inspired by other community efforts like [MohamedRashad/arabic-tokenizers-leaderboard](https://huggingface.co/spaces/MohamedRashad/arabic-tokenizers-leaderboard) and [xu-song/tokenizer-arena](https://huggingface.co/spaces/xu-song/tokenizer-arena), and aims to provide a broad, multilingual perspective on tokenizer performance.

## Metrics Explained

We evaluate tokenizers on a set of core metrics to provide a holistic view of their performance.

### 🪺 Fertility Score (Tokens/Word)
The average number of tokens generated per word. **Lower scores are better**, as they indicate that the tokenizer is more efficient at representing words.

**How it's calculated:**
The total number of tokens generated by the tokenizer is divided by the total number of words in the original text. The definition of a "word" is language-specific to ensure accuracy:
*   **For most European languages** (English, Portuguese, Spanish, etc.), we use the `Treebank` tokenizer from `NLTK`.
*   **For Vietnamese**, we use `underthesea`.
*   **For Arabic**, we use `camel-tools`.
*   **For Japanese, Chinese, and Korean**, we use `spaCy`'s language-specific models.
*   **For programming languages**, we use lexers from the `pygments` library. Comments and strings are tokenized as natural language (English using NTLK Treebank), while code constructs (keywords, operators) are treated as individual tokens.
    
You can find the exact Python code used for word counting for each language in the "Word Counting Functions" section at the end of this page.

### 🗃 Compression (Bytes/Token)
The average number of UTF-8 bytes that each token represents. **Higher scores are better**, indicating a more compact, information-dense token representation.

**How it's calculated:**
The total number of bytes in the original text (encoded in UTF-8) is divided by the total number of generated tokens.

### ⚖️ Parity (vs. Reference Language)
A measure of how a tokenizer's efficiency on a given language compares to its efficiency on a reference language (English). This metric, introduced by [Petrov et al., 2023](https://arxiv.org/abs/2305.15425), helps assess cross-lingual fairness. **Lower scores are better**.
*   A score of **1.0** means the tokenizer is equally efficient for both languages.
*   A score **> 1.0** means the tokenizer is less efficient for the target language compared to English.

**How it's calculated:**
We use the parallel [FLORES+](https://huggingface.co/datasets/openlanguagedata/flores_plus) dataset. The number of tokens generated for a text in a target language is divided by the number of tokens generated for its English translation.

### 🔄 Reversible (% docs)
The percentage of documents that can be perfectly reconstructed (losslessly) after tokenization and decoding. **Higher scores are better**, indicating that the tokenizer preserves all original information, including whitespace.

**How it's calculated:**
For each document, we check if the original text is identical to the text obtained after tokenizing and then decoding it. This is the ratio of perfectly reconstructed documents to the total number of documents.

### ❓ Unknown (% tokens)
The percentage of tokens that are marked as unknown (`<unk>`) by the tokenizer. **Lower scores are better**, indicating better vocabulary coverage.

**How it's calculated:**
The total count of the tokenizer's unknown token ID in the tokenized output is divided by the total number of generated tokens.

### ➕ Total Number of Tokens
The total number of tokens produced by the tokenizer when processing all texts within the chosen datasets. This figure is a basic count that helps contextualize other metrics but does not, on its own, serve as a direct measure of performance.

### 📘 Vocab Size
The total count of distinct tokens within the tokenizer's vocabulary. A more extensive vocabulary can result in improved fertility and compression scores (i.e., fewer tokens per word). However, this comes at the cost of a larger embedding layer in the model, which can affect memory usage and computational demands during both training and inference phases.

### 🔑 Tokenizer Hash (First 8 chars)
A unique identifier for the specific tokenizer under evaluation. This hash is generated from the tokenizer's comprehensive configuration, which includes:

- Tokenizer class information and backend details
- Vocabulary settings and special token configurations  
- Normalization and preprocessing parameters
- Model-specific settings (like SentencePiece model hashes)
- All tokenizer initialization parameters

The system creates a detailed tokenizer configuration object that captures all relevant tokenizer properties, then generates an MD5 hash from the JSON-serialized configuration (sorted by keys for consistency).

This hash serves to differentiate between tokenizers, even when they are submitted under identical model names. It's especially valuable for detecting and concealing duplicate tokenizers that are functionally the same but have been submitted under various names. For the sake of brevity, only the first 8 characters of the hash are displayed.

### 👥 Near Duplicates (% vocab)
The percentage of tokens in the vocabulary that are considered "near duplicates" of other tokens. These are tokens that differ only in minor ways, such as case, a leading prefix, or whitespace. A vocabulary with many near duplicates can be inefficient. This concept is discussed by [Stanić et al., 2023](https://arxiv.org/abs/2309.11197), [Deiseroth et al., 2024](https://arxiv.org/abs/2406.19223) and [Schäfer et al., 2024](https://aclanthology.org/2024.findings-acl.571/). **Lower scores are better**.

**How it's calculated:**
We analyze the tokenizer's vocabulary to find tokens that become identical after a series of normalization steps:
1.  **Prefix Removal**: Common tokenizer prefixes (like `Ġ` for BPE or `##` for WordPiece) are removed.
2.  **Case Normalization**: Tokens are converted to lowercase.
3.  **Whitespace Normalization**: Leading/trailing whitespace is stripped.
4.  **Unicode Normalization**: Accents and diacritics are handled to compare base characters.

Tokens that are identical after these steps are counted as near duplicates.

### ⚙️ Algorithm (Framework)
The underlying algorithm and its implementation framework used by the tokenizer. The format is `Algorithm (Framework)`.

**How it's determined:**
The implementation framework and algorithm are identified through a set of heuristics:
*   We check if the tokenizer is a "fast" tokenizer from the `tokenizers` library.
*   We inspect the tokenizer's configuration and class name (`SentencePiece`, `Tiktoken`, etc.).
*   As a fallback, we analyze the vocabulary for common prefixes (e.g., `Ġ` for BPE, `##` for WordPiece) to infer the algorithm.

## Experimental Metrics

The following metrics are **experimental** and may evolve. Some are shown by default in the leaderboard table (marked ★); the rest are hidden by default and can be enabled via the *Column Visibility* panel. The UI labels hidden-by-default columns as `[Experimental]`.

### 🧬 Byte & Character Fidelity

These metrics replace the binary **Reversible (% docs)** with continuous, document-weighted measures of reconstruction quality. Instead of asking "did the tokenizer perfectly round-trip?", they ask "how close was the round-trip?", using normalized Levenshtein edit distance.

#### 🧬 Byte Fidelity (0–1)
Corpus-level reconstruction fidelity at the UTF-8 **byte** level. For each document, the edit distance between the original byte sequence and the decoded byte sequence is computed; the per-document values are aggregated and normalized.

**Formula:** `1 − Σ(byte_edit_distance) / Σ(max(|original_bytes|, |decoded_bytes|))`

1.0 = perfect reconstruction; values below 1.0 indicate byte-level loss beyond unknown-token boundaries. **Higher is better.**

#### 📐 Effective Bytes per Token
Compression rate (bytes/token) adjusted downward for any byte-level loss. A tokenizer that achieves high raw compression but corrupts characters receives a penalty.

**Formula:** `compression_bytes × byte_fidelity`

**Higher is better.**

#### 📊 EBPB — Effective Bits Per Byte
Rate-distortion composite metric combining the per-token indexing cost (using the *observed* token cardinality, not the nominal vocabulary size) with a raw-byte fallback charge for every byte the tokenizer fails to reconstruct.

**Formula:** `(T · log₂(V_obs) + 8 · D_byte) / B`

where `T = total_tokens`, `V_obs = max(freq_cardinality, 2)`, `D_byte = byte_edit_distance_total`, `B = total_bytes`.

**Lower is better** — fewer bits per original byte of corpus.

#### 🔤 Char Fidelity (0–1) ★
Character-level sibling of Byte Fidelity. Operates on the raw Unicode string rather than its UTF-8 encoding, making it more sensitive to multi-byte characters (e.g., CJK scripts) and potentially differing from Byte Fidelity for non-ASCII-heavy corpora. **Visible by default.**

**Formula:** `1 − Σ(char_edit_distance) / Σ(max(|original_chars|, |decoded_chars|))`

1.0 = perfect reconstruction. **Higher is better.**

#### 📏 Effective Chars per Token
Compression rate (chars/token) adjusted for character fidelity.

**Formula:** `compression_chars × char_fidelity`

**Higher is better.**

#### 📈 EBPC — Effective Bits Per Char
Character-space metric combining vocabulary expressiveness with fidelity-adjusted character compression.

**Formula:** `log₂(vocab_size) / effective_chars_per_token`

**Lower is better.**

### 📊 Token Frequency Distribution

These metrics characterize how a tokenizer distributes its vocabulary usage across the evaluation corpus. They are inspired by [Zouhar et al. (ACL 2023)](https://aclanthology.org/2023.acl-long.284/) and subsequent work by [Lotz et al. (2025)](https://arxiv.org/abs/2506.03101), which showed that the shape of the token frequency distribution is strongly predictive of downstream model performance.

All metrics are computed from the token frequency counter accumulated during evaluation.

#### Coverage

*   **🔢 Tokens Seen (`freq_cardinality`):** Number of unique token IDs observed across the corpus. May be smaller than `vocab_size` when many vocabulary entries are never used. Higher values indicate broader vocabulary utilization.

*   **🔢 Tokens Seen % Vocab (`freq_cardinality_ratio`) ★:** Token cardinality divided by `vocab_size`. Shows what share of the full vocabulary was actually used. **Visible by default.**

*   **1️⃣ Hapax Count (`freq_hapax_count`):** Number of unique token types observed exactly once. High counts may signal tokenizer fragmentation or domain mismatch.

*   **1️⃣ Hapax Ratio (`freq_hapax_ratio`):** Fraction of observed types that appear exactly once. Lower values indicate more consistent vocabulary usage across the corpus.

#### Distribution Shape (Zipf)

All three metrics are computed from a linear fit on the log-rank / log-frequency curve restricted to the first ~403 ranks (log(rank) ≤ 6), where power-law behaviour is most reliable (per [Lotz et al., 2025](https://arxiv.org/abs/2506.03101)).

*   **📉 Zipf AUC (`freq_auc`):** Area under the log-rank / log-frequency curve (Simpson's rule). Larger values indicate richer, more distributed token usage.

*   **〽 Zipf Slope (`freq_slope`):** Slope of the linear fit, approximating the Zipf exponent. More negative values indicate steeper frequency drop-off (fewer tokens dominate).

*   **🔁 Power-Law Deviation (`freq_power_law`):** Mean absolute error of the linear fit. Lower values indicate the distribution follows a purer power law.

#### Entropy

*   **🌀 Shannon Entropy (`freq_entropy`):** Shannon entropy (bits) of the token probability distribution. Higher values indicate more uniform token usage and better vocabulary utilization.

*   **🌊 Rényi Entropy α=3 (`freq_renyi_entropy`):** Rényi entropy of order 3 (bits). More sensitive to high-frequency tokens than Shannon entropy. Higher is better.

#### Efficiency

Efficiency metrics normalize entropy by the log of the vocabulary size so that tokenizers of different sizes can be compared fairly.

*   **💡 Shannon Efficiency — observed vocab (`freq_shannon_efficiency`):** Shannon entropy normalized by log₂(observed unique tokens). Higher values indicate more uniform usage of the observed vocabulary. **Higher is better.**

*   **💠 Rényi Efficiency α=3 — observed vocab (`freq_renyi_efficiency`):** ★ **Identified by [Zouhar et al. (ACL 2023)](https://aclanthology.org/2023.acl-long.284/) as the single strongest predictor of downstream MT performance.** Rényi entropy (α=3) normalized by log₂(observed vocab). **Higher is better.**

*   **💡 Shannon Efficiency — full vocab (`freq_shannon_efficiency_full`):** Shannon entropy normalized by log₂(tokenizer.vocab_size). Accounts for unseen tokens; typically lower than the observed-vocab version when many entries go unused. **Higher is better.**

*   **💠 Rényi Efficiency α=3 — full vocab (`freq_renyi_efficiency_full`):** Full-vocabulary sibling of `freq_renyi_efficiency`. **Higher is better.**

#### Concentration

*   **📊 Mid-Frequency Mass (`freq_percentile_freq`):** Sum of token probabilities from the 3rd to the 83rd percentile of the descending frequency ranking. Captures how much of the corpus is covered by mid-frequency tokens. **Identified by [Zouhar et al. (ACL 2023)](https://aclanthology.org/2023.acl-long.284/) as the second-best predictor of MT performance after Rényi efficiency. Higher is better.**

*   **⚖️ Half-Mass Types (`freq_half_mass_count`):** Number of unique token types needed to cover 50% of all token occurrences. Smaller values indicate a more head-concentrated distribution.

*   **⚖️ 90%-Mass Types (`freq_90pct_mass_count`):** Number of unique token types needed to cover 90% of all token occurrences. Higher values indicate broader, more uniform vocabulary usage.

*   **📐 Token Gini (`freq_gini`):** Gini inequality coefficient of the token frequency distribution. 0 = perfectly uniform use of all observed types; 1 = a single token dominates all occurrences. **Lower is better.**

> Metrics marked ★ are visible by default. All others are hidden by default — enable them via the **Column Visibility** panel above the leaderboard table.

## Benchmark Dataset

### Creation Process
The benchmark dataset was carefully curated to cover a diverse set of languages and text domains. The process was as follows:

1.  **Manual Selection**: Over 90 high-quality datasets were selected from the Hugging Face Hub, representing various real-world text styles like news, legal documents, biomedical papers, books, and code.
2.  **Sub-domain Creation**: For each language and domain (e.g., `Portuguese - News`), text was sampled from the source datasets.
3.  **Balancing and Normalization**: To prevent larger domains from skewing the results, each sub-domain was normalized to a target size of approximately 200,000 words. This ensures that each domain contributes roughly equally to the overall metrics for a given language. During this process, language-specific word counters were used to ensure accurate word counts.
4.  **Final Dataset**: The result is a collection of `.jsonl.gz` files, each containing text for a specific language and domain, forming a challenging and comprehensive testbed for multilingual tokenizers.

## Word Count Functions

To ensure consistency and accuracy, we use specific word tokenization functions for different languages and for code. Below are the functions used to count words for the "Fertility Score" metric.

### Natural Language Word Count Functions

First, you need to install the necessary libraries and download language models for spaCy:
```bash
pip install ntlk spacy pygments underthesea camel-tools

python -m spacy download ko_core_news_sm
python -m spacy download ja_core_news_sm
python -m spacy download zh_core_web_sm
```

The Python code for tokenizing natural languages is as follows:

```python
import nltk
nltk.download('punkt_tab')
nltk.download('words')
from nltk import word_tokenize as word_tokenize_nltk
from underthesea import word_tokenize as word_tokenize_underthesea
from camel_tools.tokenizers.word import simple_word_tokenize as word_tokenize_camel_tools
import spacy

langs_nltk = {
    'en': 'english',
    'pt': 'portuguese',
    'it': 'italian',
    'pl': 'polish',
    'de': 'german',
    'es': 'spanish',
    'fr': 'french',
    'ru': 'russian',
}

langs_spacy = {
    'ja': spacy.load('ja_core_news_sm', disable=['parser', 'ner', 'lemmatizer', 'tagger', 'attribute_ruler']),
    'zh': spacy.load('zh_core_web_sm', disable=['parser', 'ner', 'lemmatizer', 'tagger', 'attribute_ruler']),
    'ko': spacy.load('ko_core_news_sm', disable=['parser', 'ner', 'lemmatizer', 'tagger', 'attribute_ruler']),
}

def word_tokenize_spacy(text, model):
    doc = model(text)
    return [token.text for token in doc if not token.is_space]

def word_tokenize(text, language):
    if language in langs_spacy:
        return word_tokenize_spacy(text, langs_spacy[language])
    elif language in langs_nltk:
        return word_tokenize_nltk(text, langs_nltk[language])
    elif language == 'vi':
        return word_tokenize_underthesea(text)
    elif language == 'ar':
        return word_tokenize_camel_tools(text)
    else:
        raise ValueError(f"Language {language} not supported")

#### Usage Example ####
word_count_pt = len(word_tokenize("Olá Mundo.", 'pt'))
word_count_ko = len(word_tokenize("이것은 한국어 문장입니다.", 'ko'))
```

### Code Word Count Function

For programming languages, we use `pygments` to distinguish between code and natural language (in comments and strings).

```python
import nltk
nltk.download('punkt_tab')
from nltk import word_tokenize

from pygments import lex
from pygments.lexers import get_lexer_by_name
from pygments.token import Token

NATURAL_LANGUAGE_PARENT_TOKEN_TYPES = {
    Token.Comment,
    Token.Literal.String,
    Token.Text,
    Token.Generic.Heading,    # For Markdown,
    Token.Generic.Subheading, # For Markdown,
    Token.Generic.Emph,       # For Markdown *italic*
    Token.Generic.Strong,     # For Markdown **bold**
    Token.Generic.Output,     # For shell output,
    Token.Generic.Error,      # Error messages
    Token.Generic.Traceback,  # Traceback messages
}

def _is_natural_language_like(tok_type) -> bool:
    for nl_parent_type in NATURAL_LANGUAGE_PARENT_TOKEN_TYPES:
        if tok_type in nl_parent_type: # This checks if tok_type is nl_parent_type OR a child
            return True
    return False

def pygments_tokenize(code: str, language: str) -> list[str]:
    lexer = get_lexer_by_name(language, stripnl=True, stripall=True)
    tokens = lex(code, lexer)

    result = []

    for tok_type, value in tokens:
        if _is_natural_language_like(tok_type):
            # Recursively tokenize comment or string content. Use the default english tokenizer.
            result.extend(word_tokenize(value))
        else:
            # Tokenize symbol/keyword/identifier at surface level
            result.append(value)

    return [t for t in result if t.strip() != '']

#### Usage Example ####
word_count_json = len(pygments_tokenize('{"hello": 1}', 'json'))
word_count_python = len(pygments_tokenize("lambda x: print('hello')", "python"))
```
